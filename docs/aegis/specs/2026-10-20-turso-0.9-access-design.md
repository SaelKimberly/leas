# Turso 0.8.2 → 0.9.0-pre.1 — Design Spec

**Status:** **PIN APPROVED and landed — `turso = "=0.9.0-pre.1"` (0.9 WAL is −24% on the
production concurrent-write shape). MVCC REJECTED on measured evidence (§7.1): on the
disjoint production shape MVCC has 0 write failures on both pins but is 75–95× slower per
batch than WAL, with tail samples spanning 2.6 s → 13.5 s; 0.9's dirty-key checkpoint did
not move the class. WAL stays the only path.** T2 (Windows) and T3 (format-drift fixture)
omitted by user decision; see §7.
**Date:** 2026-10-20
**Precedent:** `specs/2026-10-08-db-adapter-and-migrations-design.md` §12 (the owned-driver
fork, the `turso` pin policy, the "recurring version-tracking obligation"). This spec is the
next instance of that obligation and reuses its vocabulary (`src/driver/`, rsapi, the WAL
default, the MVCC opt-in).

---

## 1. Problem

`crates/leas-db` pins `turso = "0.8"` (resolving to 0.8.2) through the vendored local-only
`toasty-driver-turso` fork (`src/driver/`). Turso has published `0.9.0-pre.1`, whose engine
work targets exactly the background write/read paths this crate lives on: the MVCC
checkpoint, the MVCC cursor read, WAL checkpoint costing, connect-time serialization, and
whole-table deletes.

The question is not *whether* 0.9 helps — the engine changes are on-paper relevant to every
background task in the app. The question is what it *costs* to take a **pre-release that is
not a monotonic successor of 0.8.2**, and what must be measured before the pin moves.

Three facts frame the whole decision, each verified rather than assumed:

1. **The Rust binding is unchanged.** `bindings/rust` is doc-comment-only in the 594-commit
   delta, and the published `turso-0.9.0-pre.1.crate` exposes the same `Builder`,
   `Database::connect(&self) -> Result<Connection>` (no `ConnectOpts`), `query`, `execute`,
   `prepare`, `prepare_cached`, and `pragma_update` signatures we call. `ConnectOpts` is a
   `turso_core` API; our crate never names `turso_core` in code (two comments only). **There
   is no compile break.**
2. **The delta is a branch, not a line.** `compare v0.8.2...v0.9.0-pre.1` reports
   `status: "diverged"`, `ahead_by: 594`, `behind_by: 10`, merge base `Turso 0.8.0`.
   0.9.0-pre.1 branches off **0.8.0** and does **not** contain the 0.8.1/0.8.2 fixes. This
   is a branch switch with a regression ledger (§4), not a bump.
3. **The file format is stable in both directions.** I built a cross-version oracle (§5) and
   proved 0.9.0-pre.1 reads 0.8.2-written files and *vice versa*, in WAL **and** MVCC, with
   `header[18]`/`header[19]` identical (2/2 WAL, 255/255 MVCC). The advisory's wipe risk is
   therefore *not* the on-disk format; what remains is the generic pre-release risk plus one
   Windows build-script change (§6).

## 2. What 0.9.0-pre.1 actually changes for background tasks

Classified by subsystem, not by the word "perf" — subject-keyword grep undercounts badly
(the word appears in 15 of 594 titles). The real work is the `core/mvcc:` cluster.

| Change | Bearing on leas-db background work |
| --- | --- |
| **MVCC checkpoint collects from dirty keys, not every row** (`collect checkpoint rows from dirty keys instead of every row`; `checkpoint_state_machine.rs` rewritten ≈3,300 lines net) | The checkpoint is the largest single MVCC cost. Our own 2026-09-24 A/B measured MVCC 1.2–4.8× slower than WAL at 32 concurrent writers; the checkpoint is a prime suspect. This is the change that could reopen the MVCC verdict. |
| **MVCC cursor reads: fewer lookups and clones; cached read snapshot in scan cursors; skip per-row binding and transaction lookups; keep the table version chain found by a point seek** | Every background read under MVCC — the page query, the rank refresh, the enrichment read. |
| **B-tree deletion and conflict checking made atomic** | The delete-then-insert address-set rewrite (`update_endpoint_resolution`) and purge transactions. |
| **`wal_autocheckpoint` implemented, threshold moved onto `Connection`** (`should_checkpoint(threshold)`, default `1000`, per-connection, `set_` bumps the prepare-context generation) | **This is configurability, not new behaviour.** Correction of an earlier draft: 0.8.2 *already* auto-checkedpointed at a WAL-owned `checkpoint_threshold`; 0.9 moves the number onto the connection and makes it settable. It does not introduce background checkpointing, and it does not introduce a new stall class. Value: the cadence is finally tunable and observable per connection. |
| **`core/wal`: frame index scans start at the first frame in range** | Checkpoint cost under WAL — the default path. |
| **Pager: `init_lock` + `init_page_1` collapsed into shared `SharedPagerState`** | Connect no longer serializes on a database-wide init mutex. We open a pool **plus** a long-lived direct reader (`open_direct_conn`) **plus** an export connection — three connections that used to queue on one lock. |
| **`core/vdbe`: don't create the temp database on `BEGIN IMMEDIATE`** | Our `transactional_batch` and the write-behind flush both run `BEGIN IMMEDIATE`. |
| **`core: speed up whole-table deletes`** (with conformance coverage of every fast-path bail-out) | `clear_all_stats`, `purge_expired`, the address-set delete. |
| **`core`: shrink expression parsing and translation stack usage** | The import path is parse-heavy (~100,500 statements at the measured scale). |

Not in scope for us: the PostgreSQL frontend (47 commits), FTS (9), sync/CDC, the dotnet and
react-native bindings, the `cli/mcp` and agent-instruction noise.

## 3. What 0.9.0-pre.1 does *not* change

Verified against the published crate, so the plan does not carry phantom work:

- **No rsapi break.** `Database::connect(&self)` keeps its zero-argument signature; it passes
  `ConnectOpts` internally. The three `.connect()` call sites — `driver/mod.rs:434`,
  `database.rs:226`, `export.rs:142` — need no change. (An earlier draft of this spec led
  with a `ConnectOpts` break; that is a `turso_core`-only change and is **rejected** here.)
- **No new batch API to adopt.** `Connection::transactional_batch` already exists in 0.8.2
  (`src/connection.rs:221`, confirmed in the unpacked 0.8.2 crate). Replacing our
  hand-rolled `driver/mod.rs:148` helper with it is an **independent refactor**, not part of
  this migration, and is listed under non-goals.
- **No file-format change.** §5.

## 4. The regression ledger (the reason this is a *branch* switch)

0.9.0-pre.1 is **behind** 0.8.2 by 10 commits. The non-merge titles missing from the
0.9 line are `Turso 0.8.1`, `Turso 0.8.2-pre.2`, `Turso 0.8.2` themselves — i.e. the fixes
those releases shipped, reachable only via the merge commits (`sync: fix table refresh
replay for tables with generated columns`, `sync: rename and drop columns when an MVCC pull
refreshes a table`, `don't emit virtual columns in CDC update records`, `bindings/dotnet:
pool local databases`, `scripts: preserve external dependencies when updating versions`).
None of the named fixes is on a path leas-db uses (no sync, no CDC, no dotnet), which is
what makes the branch switch defensible — but the ledger must be **written down and
re-checked**, because the titles are merge summaries, not fix lists.

**Consequence for the plan:** the pin is a fork in the road. When stable 0.9.0 lands it
will be a *true* successor of 0.8.3, and the ledger argument changes shape. The
acceptance gate (§7) therefore includes re-deriving the ledger at pin time, not trusting
this draft's.

## 5. File format — the cross-version oracle (evidence)

The advisory flagged `database.rs:330-343`: on **any** `try_open_db` error the open path
deletes and recreates the file, so a format break would silently wipe the user database.
Rather than reason about it, I built `/tmp/xver` — a tiny crate that flips between
`turso = "0.8.2"` and `turso = "=0.9.0-pre.1"`, writes a 50–100-row fixture under one
version, and reads it under the other.

| Direction | Journal | Result | `header[18]`/`[19]` |
| --- | --- | --- | --- |
| 0.8.2 writes → 0.9.0-pre.1 reads | WAL | **100/100 rows read** | 2 / 2 (both) |
| 0.9.0-pre.1 writes → 0.8.2 reads | WAL | **100/100 rows read** | 2 / 2 (both) |
| 0.9.0-pre.1 writes → 0.8.2 reads | MVCC | **50/50 rows read** | 255 / 255 (both) |
| 0.8.2 writes → 0.9.0-pre.1 reads | MVCC | **50/50 rows read** | 255 / 255 (both) |

Both read/write version bytes and both journal headers are identical across versions. The
`file_journal_mode`/`should_use_mvcc` sniffer (`database.rs:192-217`, reading `header[19]`,
255 = MVCC) keeps its semantics: a 0.9-created file does not get mis-sniffed into the WAL
open path, and the reverse door is **not** a wipe.

The measurements stand as the one-time verification that the pin is safe in both
directions; no permanent fixture test is carried (user decision — no format drift is
expected), and no downgrade caveat is recorded in `database.md`.

## 6. The one real new risk: the Windows build script

`sdk-kit/build.rs` replaces its hardcoded `ProgramFiles(x86)\Windows Kits\10\bin\**\x64\rc.exe`
scan with `find_msvc_tools::find_windows_sdk(&CARGO_CFG_TARGET_ARCH)` — a **new
build-dependency** and an `expect()` that panics when no Windows SDK is registered.

ADR 0013 declares `x86_64-pc-windows-msvc` and CI runs `code-windows` on `windows-2022`.
**By user decision this spec does not gate on it** — the user verifies Turso's Windows
support at push time. The delta is recorded only so that check is not blind: it is the one
part of 0.9 that can break a build, it cannot break Linux, and a contributor building
locally without a registered Windows SDK now hits a build-time panic where 0.8.2 skipped.

### 7.1 Measured results (the A/B, synthetic 20,000-endpoint feed)

`flow_cost_contention`, default knobs, on 0.8.2 vs 0.9.0-pre.1:

| operation (ns/op median) | 0.8.2 WAL | 0.9 WAL | 0.8.2 MVCC | 0.9 MVCC |
| --- | --- | --- | --- | --- |
| seq geo flush BATCHED (100 rows) | 234,464 | 407,699 (**+74%**) | 760,081 | 714,731 |
| seq geo PER-ADDRESS (retired control) | 60,351 | 58,120 | 145,766 | 62,674 |
| fan-in geo PER-ADDRESS / 16 (retired control) | 9,455,328 | 8,554,849 | 610,980 | 348,305 |
| flush trickle (4,028 rows @ 12/s) | 32 flushes | 32 flushes | 32 flushes | 31 flushes |

Production-shape probe (`geo_batched_fanin_probe`, 16 writers × 16 batches × 100 rows,
shared endpoint ids, `set_endpoint_ip_countries`):

| | ok/768 | failed | ns/batch |
| --- | --- | --- | --- |
| 0.8.2 WAL, shared ids (synthetic contention) | 768 | 0 | 473,532 |
| 0.9 WAL, shared ids (synthetic contention) | 768 | 0 | 539,318 |
| **0.8.2 WAL, DISJOINT (production shape)** | **768** | **0** | **552,082** |
| **0.9.0-pre.1 WAL, DISJOINT (production shape)** | **768** | **0** | **420,572 (−24%)** |
| 0.8.2 MVCC, shared ids (synthetic contention) | 488 | **280** | 12,564,692 |
| 0.9.0-pre.1 MVCC, shared ids (synthetic contention) | 455 | **313** | 14,452,568 |
| **0.8.2 MVCC, DISJOINT (production shape)** | **768** | **0** | **41,167,764** |
| **0.9.0-pre.1 MVCC, DISJOINT (production shape)** | **768** | **0** | **39,836,786** |

**Which shape decides.** Production geo writers hold **disjoint** endpoint sets, so the
disjoint rows are the decision evidence and the shared-id rows are a synthetic worst case
kept for comparison. Two findings, both load-bearing:

1. **The abort rate is an artifact of the shared-id arm, not production behaviour.** On
   disjoint sets MVCC completes **768/768** on both pins — no `Write-write conflict` at
   all. An earlier draft of this spec argued MVCC rejection from the 280–313 shared-id
   failures; that was wrong and is corrected here.
2. **The throughput gap is decisive and 0.9 did not move it.** On the production shape
   MVCC costs **41.2 M ns/batch (0.8.2)** and **39.8 M (0.9)** versus WAL's **552 K** and
   **421 K** — **75× and 95×** respectively — with MVCC tail samples spanning
   2.6 s → 13.5 s. MVCC is not a competing path at any concurrency the app's background
   writers use; it is a different performance class.

The one WAL regression worth re-measuring before stable 0.9.0 is `seq geo flush BATCHED`
(+74%, 234,464 → 407,699 ns/op). The PER-ADDRESS rows from the retired control stay in the
first table only because the harness names them as the pre-fix baseline; they are not
production and never decided this.

Gates on the landed pin: **`just quality-gate code` 3/3 passed** (fmt; workspace clippy
`-D warnings --all-targets --all-features`; `nextest --workspace` 2499/2499, 3 slow,
11 skipped) — run on the tree with the pin, not a worktree. Earlier clean-HEAD-worktree
runs (`cargo check -p leas-db` 412 crates / 0 errors; `nextest -p leas-db` 228/228;
`nextest -p leas` 361/361) isolated the bump from the user's then-in-flight
`endpoint_rank.rs` stab-alive edit and are superseded by the workspace run.

**The stale `turso 0.7.2` lock edge is lock state, not a compiled dependency.** An earlier
draft called it an unconditional `toasty` dependency; that is wrong — the dep is
`optional = true`, our declaration enables no `turso` feature, and `cargo tree -i
turso@0.7.2` prints "nothing to print" (not in the live graph). A registry crate's
dev-dependencies never enter a consumer's graph, so the edge is not dev-dep-driven either;
it is a node left over from an older resolution that `cargo hakari` (a lock reader) cannot
prune. Disposition: **stale lock edge, build unaffected** — the workspace check already
proved no second engine compiles.

**Explicitly not in scope:** replacing `driver/mod.rs:148`'s `transactional_batch` with the
engine's (exists in 0.8.2 — independent refactor), any schema-cursor or migration work (the
DB file did not change), any change to `should_use_mvcc` semantics, and any MVCC default flip.

## 9. Risks

- **Pre-release severity.** 0.9.0-pre.1 is opt-in; a data-loss or corruption fix could land
  in 0.9.0-pre.2 with no announcement. Mitigation is the one-line pin plus the §5 oracle,
  which can be re-run in minutes against any successor version.
- **The ledger is title-level.** §4's "no path leas uses" conclusion is read off merge
  summaries. A real 0.8.1/0.8.2 fix could sit inside one of those merges and matter. T7's
  re-derivation is the guard, and it is why §4 is a ledger rather than a dismissal.
- **MVCC measurement noise.** The 2026-09-24 A/B was itself noisy ("fan-in noisy", per the
  plan). T5 reports variance, not just medians — the disjoint-arm samples
  (2.6 s → 13.5 s for MVCC) are what make the 75–95× gap credible despite that noise.
- **`wal_autocheckpoint` is per-connection.** Set at only one site it silently does nothing
  for pooled connections — the exact failure mode of the historical `busy_timeout` storm.



## 10. Non-goals

- No `SCHEMA_VERSION` bump, no `Step::Rebuild`, no wipe: the file format is unchanged (§5).
- No MVCC default change (§7 T5).
- No `transactional_batch` refactor (§3).
- No re-litigation of the owned-driver-fork decision; 0.9 changes none of its premises.
