# TLS fingerprint roster: JA4 fidelity evidence

This page records why the kept browser-hello roster is trustworthy: the roster's scale, the two hand-transcribed slots, the fidelity contract the code enforces, and the live sweep against `tls.peet.ws` with its measurements and dates. It does not describe the TLS engine, the JA4 variants, or the era-gating rules for post-quantum key shares; those belong to [`native-core.md`](native-core.md) and [`decisions.md`](../architecture/decisions.md). Roster membership and per-entry JA4 values are owned by `crates/leas-tls/src/profiles/generated/` and enforced by the tests named below.

**Roster:** 71 kept profiles = 69 generated JA4-faithful + 2 wire-exact hand (`chrome_130`, `edge_106`).
**Live target:** `https://tls.peet.ws` (`/api/all`, TLS 1.3, HTTP/2 + HTTP/1.1).
**Result of the 2026-08-25 sweep:** 71/71 passed both full runs; every kept entry connected and returned its expected JA4, and the two hand profiles returned their hand-captured JA4.

Provenance: the roster reduction and the sweep ran 2026-08-25. The emitted roster was last regenerated by `gen_specs.py --emit` on 2026-11-05 (era-correct key shares, explicit JA4). Regeneration is byte-deterministic and checked by `--selftest`, so the committed files, not a branch name, are the provenance.

| Flag | Effect |
| --- | --- |
| `--manifest` | rebuild `specs_manifest.json` from the ja4db export (attribution/join/dedup; stats printed) |
| `--emit` | render `profiles/generated/*.rs` from the manifest, byte-deterministic |

Run `--manifest` before `--emit` and commit both: the manifest caches the synthesized wire bodies, so `--emit` alone re-renders the old bodies and silently reverts a body fix. The corpus quirks that make a 100% set-level round-trip impossible (46 parsed strings with an A-part absent from the hash export, 5 corrupt hashed keys, and similar) are documented in the generator header, with its asserted floors of 898/998 parsed strings and 264440/267622 observation-weighted matches.

## The two hand-upgraded slots

The wire-exact upgrade rule: a hand profile whose JA4 shares the A-part and the cipher hash with a kept cluster, and whose (browser, os, device) triple equals the cluster's triple, replaces the top-ranked matching slot. One hand profile fills one slot.

| Hand profile | Triple | Replaces | Expected JA4 on tls.peet.ws |
| --- | --- | --- | --- |
| `chrome_130` | chrome / windows / desktop | `chrome_148_windows_desktop` | `t13d1516h2_8daaf6152771_f37e75b10bcc` |
| `edge_106` | edge / windows / desktop | `edge_149_windows_desktop` | `t13d1516h2_8daaf6152771_f37e75b10bcc` |

Both were transcribed byte for byte into `spec!` tokens from the original hand modules (deleted; the equality was pinned by the removed `hand_selected_matches_original_wire_bytes` equivalence test). The two slots differ from each other: `chrome_130` offers `compress[0x0002, 0x0003]` and one GREASE extension, `edge_106` offers `compress[0x0003]` and two GREASE slots.

They share one JA4 because peet.ws reports the **PeetWs** variant of the JA4 encoder, which excludes the padding extension from the extension hash. The value `f37e75b10bcc` is that rendering of the same canonical Chrome hello: `crates/leas-tls/src/crypto/fingerprint/ja4.rs` asserts `hash2_variant(foxio_vector(), Ja4Variant::PeetWs) == "f37e75b10bcc"` against the FoxIO published example, whose `Foxio`-variant hash is `e5627efa2ab1`. The kept clusters it was compared with render under the corpus (FoxIO) rule: `t13d1516h2_8daaf6152771_02713d6af862` (Edge 128, Chrome 122) and `t13d1516h2_8daaf6152771_d8a2da3f94cd` (Edge 137). The A-part and cipher hash therefore match the cluster; the extension hash differs by the padding rule. The live sweep confirms both slots return `f37e75b10bcc` exactly. The two variants are documented in [`decisions.md`](../architecture/decisions.md).

## Fidelity contract

Every kept entry's built ClientHello must reproduce its registered source JA4 (`GenEntry.ja4`; for the hand profiles, the hand-captured value).

**Offline gate** (`crates/leas-tls/tests/generated_ja4_gate.rs`, runs in every `cargo test`). The test builds all 69 generated entries with the fixed-seed RNG, parses each hello, and recomputes JA4 with the crate's own codec. The enforced contract, asserted to the class level:

| Class | Count (current) |
| --- | --- |
| Full-hash exact | 66 |
| Padding in hello | 0 |
| Padding omitted | 0 |
| No signature algorithms | 0 |
| `ht` A-part letter | 3 |
| Failures | 0 |

The 3 residual entries differ only in the A-part ALPN letter: the corpus renders `http/1.1` as `ht` (first two characters) and the FoxIO rule takes first plus last (`h1`). The encoder moved to the FoxIO default (padding `0015` kept in the extension hash), which absorbed the earlier padding classes; the gate's assertions carry that derivation. A drift in any class fails the gate, and the roster must then be re-derived from the manifest.

The two hand profiles are pinned offline by `crates/leas-tls/tests/tls_peet_ws.rs::local_fingerprints_match_locked_constants` (`chrome_130` JA4 v2 and GREASE-stripped JA3 md5 under the fixed seed) and by the resolver JA4-fidelity tests.

**Live sweep** (`cargo run -p leas-tls --example grader -- --roster`) is the empirical confirmation against the real peet.ws API. The grader walks the combined roster (`profiles::combined_roster`, the 69 generated entries plus the 2 hand profiles).

## Live sweep methodology

For each entry: build the ClientHello from the spec with the fixed-seed fixture (all-`0x5A`), parse it locally, then open a real TLS 1.3 connection to tls.peet.ws (per-connection GREASE via `SystemRandom`; JA4 is GREASE-normalized, so the fixed-seed local value stays comparable). Check the server's reported JA4 against two references:

1. the local JA4 computed with the server's own algorithm (wire fidelity);
2. the registered expected JA4 (corpus value for generated entries, hand-captured value for the hand profiles), normalized for the server's rendering.

The sweep runs 16 concurrent connections with a 20 s per-entry cap. The server's `ja4.go` rendering differs from the FoxIO spec in ways the grader replicates:

- A-part counts are non-padded decimal, and the ALPN letter is omitted when no ALPN is offered (registered `t13d170900_…` reports as `t13d179_…`);
- the extension hash excludes padding `0015`.

Entries whose hello offers no `h2` ALPN (the 3 `http/1.1`-only and the 14 no-ALPN entries) are graded over an HTTP/1.1 GET (`Connection: close`, Content-Length/chunked aware).

## Findings

### Finding 1: `0x0029` (pre_shared_key) exclusion (historical)

The pre-reduction roster had 111 entries carrying `raw[0x0029, ""]`. peet.ws (Go `crypto/tls`) deterministically rejects any hello with it (fatal `unexpected_message`), so those entries were live-connect-infeasible. The kept roster excludes PSK by construction (`select_roster` drops `0x0029` carriers) and the emit-time `EMPTY_BODY_ILLEGAL` set refuses to render a bodyless `pre_shared_key`, so no kept entry can hit this rejection. The sampled test keeps its PSK filter as a harmless guard.

### Finding 2: empty bodies (the 2026-08-25 "accepted" verdict was wrong; fixed 2026-09-17)

36 kept entries carried the empty ECH GREASE outer (`fe0d`) and 28 carried an empty `compress_certificate` list. Both connected and graded cleanly against tls.peet.ws, and the sweep concluded they were fine because "the server treats it as an unknown extension (RFC 8446 §4.2)". That was true of the Go peer and false where it matters: BoringSSL (Cloudflare, Google, and the proxy hosts a real batch talks to) parses `encrypted_client_hello` and `compress_certificate`, and answers `alert 2 50 (decode_error)` to a body its RFC forbids.

Measured 2026-09-17: `alert 2 50` appeared on exactly the fingerprint ids that resolve to those rows (firefox 37, ios 6, safari 4 of 3,380 phase-2 failures), and an A/B on one link config with only `security.fp` swapped (same host, SNI, ALPN) completed the handshake for `chrome`/`edge`/`randomized` while `firefox`/`ios`/`safari` got `decode_error` in 0.1 s; six Cloudflare-fronted hosts repeated it 6/6. Removing the extension from the resolved row made the probe pass; removing the empty `compress[]` did the same for Safari.

The class was one emitter mistake repeated: `gen_specs.py` synthesizes bodies from an id-only corpus (ALPS body length fixed 2026-09-16, then ECH, the compression list, and `delegated_credentials`' sig-alg vector). Current behaviour:

- `build_extension` names ECH to the engine's `EchGrease` variant, which draws a body per connection (a constant body would give every connection of an identity identical bytes), synthesizes the two sig-alg vectors like `signature_algorithms_cert`, and substitutes `brotli` for an empty `compress_certificate`;
- `_ext_token` refuses to emit a bodyless extension whose id is in `EMPTY_BODY_ILLEGAL`;
- `profiles::tests::every_roster_hello_has_rfc_minimal_extension_bodies` sweeps every emitted hello for each extension's RFC minimum.

Tier 2's `crates/leas-tls/tests/strict_peer_presets.rs` is the live oracle for the class this page's own sweep cannot see: a lenient peer grades a malformed body as clean.

### Finding 3: `http/1.1`-only and no-ALPN entries (3 + 14)

- 3 `ht`-letter entries (`brave_89_windows_desktop`, `brave_90_macos_desktop`, `firefox_138_ios_phone`; ALPN `http/1.1` only) are graded through the HTTP/1.1 GET path. The server renders the A-part letter `h1` (first plus last, matching the crate codec), while the corpus `ht` is the ja4db first-two-characters rendering. The difference keeps their registered-match flag clear; they are never full-hash class, so it is not a failure.
- 14 no-ALPN entries connect over HTTP/1.1 by default; the server omits the A-part letter entirely and uses non-padded counts.

### Finding 4: low-fidelity slots (JA4-faithful tier, by design)

2 of the 69 kept generated entries are flagged `low_fidelity` in the manifest (`chrome_93_windows_desktop`, `chrome_83_android_tablet`): their byte-level wire shape (sig-alg ordering, extension bodies) is synthesized, not observed; only their JA4 is corpus-faithful. The other 67 are JA4-faithful: they reproduce the registered JA4 exactly (pinned offline and live) while their byte-level shape may diverge from a real browser. JA4 reproduction is the contract, not byte-level wire mimicry.

Separately, two low-fidelity generated slots (`chrome_148_windows_desktop`, `edge_149_windows_desktop`) were replaced by the wire-exact hand profiles `chrome_130`/`edge_106` (transcribed from real browser hellos), so they are not part of the 69.

### Finding 5: dropped artifacts (historical)

- `chrome_619_windows_desktop` (spoofed-UA artifact, 35,850 corpus observations) and other out-of-range majors are excluded by the family sanity floors/caps (chrome 80 to 155, and so on).
- The empty-`0x0032` (`signature_algorithms_cert`) template bug found by the original 1825-entry sweep was fixed in the generator (synthesized RFC 8446 §4.2.3 default body) and is gone from the regenerated roster.

## Reproduction

```bash
# Full live sweep over the kept 71 (69 generated + 2 hand), about 5 s
cargo run -p leas-tls --example grader -- --roster
# Per family, or per (family, major)-band sample (hand profiles claim their band)
cargo run -p leas-tls --example grader -- --roster --family chrome
cargo run -p leas-tls --example grader -- --roster --sample
# Offline gate (no network; runs in every cargo test)
cargo test -p leas-tls --test generated_ja4_gate
# Offline hand-profile pins, plus the sampled live test (one entry per
# family/band, hand profiles included; ignored by default)
cargo test -p leas-tls --test tls_peet_ws
cargo test -p leas-tls --test tls_peet_ws -- --ignored
# Generator self-check (kept-set regeneration is byte-deterministic)
python3 crates/leas-tls/src/fingerprints/catalog/gen_specs.py --selftest
```

The grader's `--roster` mode prints per-entry lines (`name family class ht ech alpn server_ja4 error`) and a per-family summary (full / pad+ / pad− / no-sig / ht / wire-ok / reg-ok / fail). With `--sample`, the wire-exact hand profiles claim their (family, major) band first: `chrome_130` shares band 130 with the generated `opera_130_*` entries, so the sample always covers them.
