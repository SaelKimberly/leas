# Turso 0.9.0-pre.5: what changed, and what it is worth to this DB layer

Evidence study, 2026-11-16. Baseline: `turso = "=0.9.0-pre.5"` as pinned in
`crates/leas-db/Cargo.toml`, the `dump-4.log` session (2026-11-13 07:53 →
2026-11-16 07:53, 72 h), and a fresh versioned clone of the engine at
`thirdparty/turso` carrying the full `v0.8.2..v0.9.0-pre.5` history (2 428
commits; the previous shallow clone held one commit at the `v0.8.2` tag).

Reproduction: `cargo test -p leas-db --release --features perf-lab --test
turso09_lab -- --ignored --nocapture --test-threads=1` (each row prints its own
line: `IMPORT`, `SINGLE`, `PURGE`, `WIDTH`, `PROTOS`). The lab measures the
process itself: CPU from `/proc/self/stat`, peak RSS from `VmHWM`, disk split
into the DB file, `<db>-wal` and `<db>.db-log`.

Every number below is measured on this machine (Linux 6.8, release build) or
quoted from the engine's own source/docs with a path; nothing is estimated from
a blog post. The engine publishes **no release notes** for the 0.9 pre-releases
(`CHANGELOG.md` stops at 0.8.0, the GitHub release body is the bare version
string), so the delta below comes from history and from the docs at the tag.

## 1. The 0.8.2 → 0.9.0-pre.5 delta that matters here

| Capability | State at 0.9.0-pre.5 | Evidence |
| --- | --- | --- |
| MVCC journal mode | declared **production ready** (the "do not use for critical data" warning removed) | `git show 01933d47d` — `docs/manual.md`, `COMPAT.md` |
| Window functions | `ntile` and `lag` verified against the pinned crate (`window_functions_and_recursive_cte_answer_correctly`); the reference page claims the full SQLite set including `percent_rank`/`cume_dist`, `lag`/`lead`, custom `ROWS`/`RANGE`/`GROUPS` frames, `EXCLUDE` and `FILTER (WHERE)` | lab smoke test + `docs/sql-reference/functions/window.mdx`; the `COMPAT.md` row still claims the navigational functions are missing, so that row is stale |
| `WITH RECURSIVE` | supported, verified (the recursive count query answers 5) | `01933d47d` + lab smoke test |
| `LATERAL (subquery)` | Turso extension, supported | `docs/sql-reference/statements/select.mdx` |
| `PRAGMA synchronous` | `NORMAL` documented as "no fsync on commit, fsync at checkpoint" | `docs/sql-reference/pragmas.mdx`; the *code* already mapped `NORMAL` at `v0.8.2` (`core/translate/pragma.rs:672`) and only the docs were stale, so the durability behaviour is not a new win |
| `PRAGMA wal_autocheckpoint` | newly supported | `COMPAT.md` diff |
| `PRAGMA mvcc_checkpoint_threshold` / `mvcc_gc_threshold` / `mvcc_group_commit` | present; checkpoint threshold default **4 120 000** (bytes of logical log) | `core/mvcc/persistent_storage/logical_log.rs:270`, `docs/sql-reference/pragmas.mdx` §MVCC Tuning |
| `VACUUM INTO` | supported; in-place `VACUUM` still experimental | `COMPAT.md` |
| Generated columns | no longer behind an experimental flag | `COMPAT.md` diff |
| `auto_vacuum` | experimental, needs `--experimental-autovacuum`; `incremental` unsupported | `docs/sql-reference/pragmas.mdx` §auto_vacuum |
| Materialized views | experimental (IVM) | `COMPAT.md` |
| `WITHOUT ROWID` | insert-only, still experimental | `COMPAT.md` row unchanged |

MVCC internals relevant to us, from the engine's own docs and code:

- checkpoints are triggered by the logical-log byte threshold above, not by row count; on the commit path;
- the default checkpoint mode is `Truncate`, which **blocks readers and writers** for its duration; `experimental_mvcc_passive_checkpoint` switches it to a non-blocking `Passive` drain and is also the gate for issuing `PRAGMA wal_checkpoint(PASSIVE)` (`core/translate/pragma.rs:1008-1017`);
- `leas-db` already pairs the flag with the MVCC opt-in (`crates/leas-db/src/database.rs:260-280`), so the MVCC arm measured below is the tuned configuration, not the blocking default;
- per-row MVCC heap, from the engine's own `perf/memory` tool at 100k rows × 100 B blob (`git show 318878818`): insert 661.8 B uncommitted / 843.7 B at commit peak / 664.3 B after commit; update 781.8 / 1 047.6 / 784.3; delete 661.8 / 731.0 / 664.3.

## 2. MVCC against WAL on the leas workloads

Feed: 40 000 endpoints + protocols + links preseeded, then a 20 000-row import
burst over it (`BATCH` 400, one transaction per chunk — the shape
`upsert_endpoints_bulk` / `upsert_links_bulk` issue), with a page reader on its
own connection reading a 20-id page every 20 ms.

| Metric | WAL | MVCC | Δ |
| --- | --- | --- | --- |
| import wall (+20k rows) | 1.11–1.30 s | 2.21–2.57 s | **+70…130 %** |
| CPU (utime+stime) | 1 730–2 250 ms | 3 690–4 320 ms | **+64…150 %** |
| peak RSS | 56–69 MiB | 154–184 MiB | **2.6–2.7×** |
| RSS growth over the burst | +4…+23 MiB | +25…+52 MiB | 2–6× |
| disk after the burst | db 18.0 MiB + wal 16.0 MiB | db 15.7–19.7 MiB + wal 8.3–12.3 MiB + log 0.3 MiB | similar total |
| page read (20 ids), quiet DB | p50 19.1–19.7 ms | p50 33.1–35.1 ms | **~1.8× slower** |
| page read (20 ids), during the burst | n≈21–30, p50 28.5–29.8 ms, p95 34.9–39.2 ms, max 36.8–42.8 ms | n=30, p50 55.2–61.4 ms, p95 72.6–111.3 ms, max 80.4–140.8 ms | **~1.9× p50, up to 2.8× p95, 3.3× max** |
| 500 one-row transactions through `retry_on_busy(_, 5)` | 122–198 ms, 0 failures | 78–88 ms, 0 failures | **1.6–2.2× faster** |

The one MVCC win is the single-row commit path; the workload that dominates
this app is the opposite one (batch import plus page reads every frame), and
there MVCC costs 1.6–1.9× CPU and 2–3× peak memory while making the page read
slower both quiet and under load. The per-row heap numbers from the engine's
memory tool explain the RSS delta: a 20 000-row transaction holds ~660–1 050 B
per written row until a checkpoint.

The dump's 39.6 s page read is therefore **not** an argument for MVCC: the same
stalls are what the passive checkpoint targets, but switching modes makes every
ordinary read slower in the measurement above. If the stalls reappear, the
honest experiment is to run the same import with `LEAS_TURSO_CONCURRENT_WRITES=1`
for one session and compare the `slow query` distribution — the lab already
reproduces both arms.

## 3. The orphan-protocol anti-join (the 508 s finding) survives the pin bump

74 000 protocols, 5 % without a link, both journal modes:

| Shape | WAL | MVCC |
| --- | --- | --- |
| toasty `NOT (id IN (SELECT protocol_id FROM profile_stats))` | **5.37 s** | **5.39 s** |
| `NOT EXISTS (SELECT 1 FROM profile_stats p WHERE p.protocol_id = protocols.id)` | **23.5 ms** | 76.1 ms |
| `DELETE FROM protocols WHERE NOT EXISTS (…)` | 30.0 ms | 97.8 ms |

So: the mode-independent 230× gap is still there at 0.9.0-pre.5 (it is a
per-row subquery loop in the planner, not a journal-mode property), and under
MVCC the same rewrite is 3× slower than under WAL because the write path pays
for version chains and the logical log.

## 4. A schema split does NOT fix that scan

The obvious restructuring candidate — move `protocols.config` (the one large,
write-mostly JSON column, 405 B per row in this feed) into a side table so the
scanned row is narrow — was measured directly: the same 74k feed with the
realistic config and with the bare object a split would leave.

| Feed | DB file | `NOT IN` | `NOT EXISTS` |
| --- | --- | --- | --- |
| realistic config | 22.8 MiB | 5.34 s | 23.4 ms |
| bare config | 17.5 MiB | 5.36 s | 23.2 ms |

Config width changes the file by 5.3 MiB and the anti-join by nothing: the cost
is per-row subquery evaluation, not bytes read. **Splitting `protocols` would
buy disk and no query time**; any such change has to be justified by its own
measurement, not by this query.

## 5. One import family is 4.6× slower than its siblings

`upsert_protocols_bulk` issues ONE typed upsert per protocol, while every other
import family is a 400-row literal statement. 20 000 protocols, same
transaction-per-400-rows shape, two runs:

| Shape | Wall |
| --- | --- |
| typed, one statement per protocol (current) | 658–713 ms |
| one literal statement per 400 rows | **125–155 ms** |

That is ~27–28 µs per protocol of pure statement overhead — a 100k-protocol
feed pays ~3 s in it. The fix is one bulk writer mirroring
`upsert_endpoints_bulk`, with the same `ON CONFLICT(id) DO UPDATE` column set
`upsert_protocols_bulk` already declares.

## 6. Recommendations, in the order the evidence supports them

1. **Rewrite the orphan purge to the `NOT EXISTS` form** (one `DELETE … WHERE
   NOT EXISTS`), and run it once per compact pass instead of once per merged
   endpoint. 5.37 s → 23 ms per pass, mode-independent, no schema change.
   Precedent: `purge_expired_once` already uses raw SQL for the same reason.
2. **Chunk `upsert_protocols_bulk`** to the 400-row literal shape: 4.6× on that
   family, no contract change (same column set, same `DO UPDATE`).
3. **Stay on WAL.** MVCC at 0.9.0-pre.5 is production ready and correctly tuned
   here (passive checkpoint is already paired with the opt-in) but measures
   slower on every workload except the single-row commit, and 2–3× higher peak
   memory on the import.
4. **Do not restructure the schema for the anti-join.** The measured candidate
   (narrowing `protocols`) changes nothing; a split needs its own workload
   evidence first.
5. **Log the journal mode at open** (`journal_mode`, concurrent-writes flag,
   `synchronous`) — a dump still cannot say which mode produced it, which is
   exactly the ambiguity this study had to remove by experiment.
6. Only if page stalls return: `PRAGMA mvcc_checkpoint_threshold` is the
   knob to raise (default 4.12 MB of logical log), and `mvcc_gc_threshold`
   the one to lower memory at the cost of GC work. Both are measured by the
   same lab once the pin moves.

## 7. Limits of this evidence

- The feed is synthetic at the dump's scale (74k protocols, 20k-row bursts),
  not the operator's file: same statement shapes, different data
  distribution. `NOT IN` cost tracks protocol count, which is matched.
- The reader arm has ~30 samples per arm at a 20 ms cadence; the MVCC/WAL
  read gap repeated across three runs, the exact p95 has run-to-run spread of a
  few ms.
- One machine, one allocator configuration (the app's mimalloc is not installed
  in the lab process, so RSS is the system allocator's).
- `percent_rank`/`cume_dist` and custom frames are documented but not measured
  here; only `ntile`, `lag` and `WITH RECURSIVE` ran against the pinned crate.
