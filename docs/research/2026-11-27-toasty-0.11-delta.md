## 1. Headline

1. **The release is about relations and engine internals, not about the API
   surface this crate uses.** Six of the eight features are polymorphic/embedded
   relations, MariaDB, `jiff::tz::TimeZone` and PostgreSQL `Vec` uniqueness — all
   things `leas-db` does not model (§2). Our layer is typed single-table CRUD
   plus raw SQL for the hot paths, and the raw SQL is untouched by a toasty
   release.
2. **0.11 is the version that lets this workspace resolve at all.**
   `toasty-driver-turso 0.10` requested `turso ^0.7` with default features
   (the driver is declared optional, yet cargo still resolves it into the graph
   with `default-features = false` and no backend feature enabled — verified
   with `cargo metadata`), which pulls `libmimalloc-sys`
   (`links = "mimalloc"`); this binary links `rustfs-mimalloc-sys 0.7.4`
   (`links = "mimalloc"`), so pinning toasty back to `=0.10.0` makes the
   workspace **unresolvable** (§5.1). 0.11's #1234 requests turso with
   `default-features = false`. The upgrade was not cosmetic — it is the floor
   for an app that owns `#[global_allocator]`.
3. **Breaking changes we absorbed silently**, worth knowing before any future
   pin move: newtype field handles are `inner()` not `_0()` (#1183);
   `Model::OneField` carries the relation target (#1249);
   `Capability::returning_from_mutation` split into `returning_from_insert` /
   `returning_from_update`; `ExecResponse` cursors are boxed;
   `ExprInSubquery`/`ExprIsNull` carry a `negated` flag (public struct fields).
   Our source never names any of them; only the vendored driver touches the
   driver contract, and it compiled unchanged because it reads
   `Capability::TURSO`.
4. **One dead lint allowance, verified** (§5.2): the crate-level
   `clippy::used_underscore_binding` allow in `models_toasty.rs` no longer
   suppresses anything at 0.11 (0 hits with it removed, rustc 1.100.0). The
   `used_underscore_items` allow next to it is still required (5 hits).
5. **No bulk, upsert or migration additions in this range.**
   `create_many()`/`batch()` and the CLI migration framework predate 0.10; the
   0.11 diff only clarifies MySQL's batch-ID limits. The index story likewise did
   not change: a field-level `#[index]` is one column, a **struct-level**
   `#[index(a, b)]` has expressed ascending composites since before 0.10, and
   neither carries per-column `ASC`/`DESC` (§6.2 re-reads our hand-written DDL
   against that).

## 3. Statement-layer changes that touch semantics

- **`NOT IN` and `IS NOT NULL` are first-class predicates.** `ExprInSubquery`
  and `ExprIsNull` gained `negated: bool`; `Expr::not_in_subquery` is new; the
  SQL serializer now renders `NOT IN (` / ` IS NOT NULL` directly
  (`crates/toasty-sql/src/serializer/expr.rs`). The reason (from the struct
  docs) is that variant guards attach to the predicate before a negated form is
  expanded, so the guards end up outside the negation.
  For us this is documentation, not a lever: the shipped orphan purge is raw
  `DELETE … WHERE NOT EXISTS` (`database.rs:2890`), and the typed
  `links().all(FALSE)` shape survives only in a comment. If a typed
  false-predicate ever returns, 0.11 will emit `NOT IN (…)`, not
  `NOT (… IN (…))` — `[INFERENCE]` from the serializer diff that this is also
  the shape the engine prefers; it was not measured.
- **`merge_in_subqueries`** (`engine/simplify/merge_in_subqueries.rs`, new,
  275 lines) folds `x IN (q1) OR x IN (q2)` into one membership test when the
  queries share a source. We have no typed `in_query`/OR-of-IN anywhere
  (verified), so it cannot affect a statement this crate issues.
- **Option semantics are specified, not implemented.** `docs/dev/design/option-semantics.md`
  (new, 179 lines) and `docs/dev/roadmap/option-semantics.md` are explicit:
  Rust `Option` presence rules are the *target*, implemented "in separate PRs"
  for representation, presence, equality and membership. No commit in the range
  implements it, so today's SQL behaviour stands (`ne(x)` still excludes NULL
  rows; the design only defines their future behaviour). The typed predicate
  inventory in `crates/leas-db/src` (verified): one presence test —
  `Group::fields().url().is_some()` (`database.rs:1267`) — two membership tests
  over required ids (`in_list(Endpoint::fields().id(), …)`, `database.rs:2193`,
  `merge.rs:150`), and `eq` filters only (`protocol_id`, `enabled`, `group_id`,
  `endpoint_id`, `id`). There is no `ne(`, no `not(`, no `is_none(`.
  The design's truth table leaves those shapes as they are (`eq` on present
  values, presence for `is_some`, required candidates lifted into `Some`); the
  rows that change meaning are `ne` over optional fields and membership with
  `None` candidates. Re-audit trigger: if either appears before toasty ships
  the contract, re-read it then.
- **SQLite SQL output did not change.** The `toasty-sql` diff is MariaDB arms,
  PG enum quoting, and the negated-predicate rendering above; the type mapping
  diff has no SQLite line. So no generated-SQL drift for our backend `[INFERENCE]`
  beyond the negated predicates we do not issue.

## 4. Driver contract (the seam our fork owns)

The crate does **not** use `toasty-driver-turso`: `cargo tree --workspace -i
toasty-driver-turso` prints nothing, and `turso 0.7.2` in `Cargo.lock` is the
inert optional-driver resolution `[INFERENCE]` — it is not in the build graph.
What 0.11 changed on the contract our fork implements:

| Change | Effect on `crates/leas-db/src/driver/` |
| --- | --- |
| `Capability::returning_from_mutation` → `returning_from_insert` + `returning_from_update` | none: the fork returns `Capability::TURSO` (both `true`); a fork that builds its own capability must set both |
| `Capability::unique_list_index` flag, `Dialect::MariaDb` | none (SQLite path) |
| `ExecResponse::next_cursor`/`prev_cursor` boxed | none: our responses never set cursors |
| `Operation` docs: `Insert` is sent to every driver | already true for us |
| `Driver::max_connections()` (new, default `None`) | uncapped; pool = deadpool default `2 × cpu`. Our driver caches one `turso::Database`, so a cap is not needed for correctness; it is the hook to use if a connection budget is ever wanted |
| `toasty-driver-turso` grows a `conn.rs` serverless dispatch layer (234 lines) and ~1 000 lines of cloud plumbing | upstream only; our fork stays local-only for the reasons in its header (unbounded `prepare_cached` keyed by inlined SQL text, and a direct `turso` pin) |

The fork's header comment still says `turso` is "pinned directly (currently
0.8.2)" while the crate pins `0.9.0-pre.5` — stale text, no code effect.

### 5.3 In-memory pooling (the `max_connections` question)

```sh
cargo nextest run -p leas-db in_memory_db_has_full_schema_and_roundtrips
# PASS [0.060s] leas-db::integration in_memory_db_has_full_schema_and_roundtrips
```

That test creates the schema on one pooled connection and reads it back through
another (`db.get_endpoint(…)` takes a fresh pool slot), which only passes if the
cached `turso::Database` is shared across slots — the same property that makes a
`max_connections` cap unnecessary (§2). Turso's source agrees:
`Database::connect`/`connect_with` build a new `Connection` on `self` (the
`Arc<Database>`), not on a fresh store.

## 6. Recommendations, ranked

1. **Delete the `used_underscore_binding` allow** in
   `crates/leas-db/src/models_toasty.rs` and trim the `_0` sentence from the
   neighbouring `used_underscore_items` reason (the newtype field is `inner`
   now; the five remaining hits are field *types*). Evidence: §5.2.
2. **Keep the raw-SQL writers, and re-read one DDL claim.** Nothing in
   0.10→0.11 adds bulk insert/upsert or a migration path that replaces the raw
   writers (`create_many`/`batch` and the CLI migrations existed before 0.10).
   On indexes the release changed nothing either, but the audit found our
   reason text stale: `schema/ddl.rs::ENDPOINT_IP_BY_KEY` says the
   `(ip_key, endpoint_id)` order "toasty's per-field `#[index]` cannot express"
   — true for the field attribute, false for the **struct-level**
   `#[index(name = "endpoint_ip_by_key", ip_key, endpoint_id)]`, which has
   existed since before 0.10 (`toasty-macros`' `ModelAttr::indices`, guide
   §Struct-level `#[index]`). Mixed-direction composites (`endpoint_rank_key_v2`
   with `rank_weight DESC`, `endpoint_rank_band_window` over raw columns) stay
   raw regardless: `KeyAttr` carries fields and a name, not a direction.
   Recommendation: fix the comment. Moving the index into the model is a
   trade-off, not a win — the model path creates it only when `push_schema` runs
   at cursor 0, while the raw statement re-applies on every open and so heals a
   database that lost the index.
3. **Treat 0.11 as the floor.** Any future pin below 0.11 (or a git revision
   before #1234) breaks resolution against the app's allocator. Put that in the
   bump note if `toasty` is ever re-pinned.
4. **Watch Option semantics, change nothing yet.** Today's SQL behaviour is
   what runs; the contract is doc-only (§3). The crate's typed predicates are one
   `is_some()`, two `in_list` over required ids, and `eq` filters — none of which
   the contract's table changes — and no `ne`/`not`/`is_none` exists. Add those
   three APIs to the review checklist for any future bump that implements the
   contract.
5. **Do not cap `max_connections`.** The new hook is not a correctness gap here:
   our driver shares one cached `turso::Database` across pool slots, so
   `:memory:` behaves like a single database without a cap (§2 row), and a cap
   would serialize file-backed reads. The hook is the place to set a cap only if
   an operational connection budget ever exists.
6. **Do not adopt** polymorphic relations, `EmbedCreate`, `jiff::tz::TimeZone`,
   MariaDB, unique `Vec` fields, borrowed JSON setters, or the serverless turso
   transport. Each is real and well-tested upstream; none has a caller here.

## 7. Re-audit recipe for the next bump (0.11 → 0.12)

1. `crates/*/CHANGELOG.md` at the new tag is the canonical feature list — the 41
   commits here produced exactly one changelog entry each; start there, then map
   each entry onto §2's table.
2. Re-run §5.1's resolution matrix first: an allocator/driver collision is a
   showstopper that no code review catches.
3. Re-run §5.2 for both allows; the macro output keeps shifting under clippy.
4. Diff `crates/toasty-sql/src` — any change in the SQLite arms changes the SQL
   our typed queries emit, which is the only place an ORM bump can move our
   database behaviour.
5. Diff `crates/toasty-core/src/driver/` — that is the contract the vendored fork
   implements; a changed trait method is a compile break in our code, not
   upstream's.
6. If ratios matter: `cargo nextest run -p leas-db` plus the perf-lab arms
   (`import_wal_vs_mvcc`, `plan_sweep`) are the only local measurements that see
   a toasty change, because the typed path they exercise is the same one the app
   uses for single-row CRUD.

## 8. Limits of this evidence

- Both versions cannot coexist in one workspace (§5.1), so there is **no A/B
  timing**; every performance statement is upstream's own and is quoted as
  such.
- "Not used here" verdicts are from grepping `crates/leas-db/src` for the
  feature's API (`include`, `in_query`, `not`, `ne`, `is_none`, `_0()`,
  data-carrying enum variants, `Json` clone sites) — they describe today's tree,
  not future code.
- The 12 post-0.11 commits in the manifest's pinned `main` commit were classified
  from their subjects and the compare API; their diffs were not read (they are
  outside the requested range).
- Crate-vs-tag identity was checked on `toasty` and `toasty-macros` only; the
  other six 0.11 crates share the same `.cargo_vcs_info.json` sha.
