# Turso v0.9.0-pre.5 → v0.9.0-pre.6: delta review for `leas-db`

Evidence study, 2026-11-27. Baseline: `turso = "=0.9.0-pre.5"` in
`crates/leas-db/Cargo.toml`; candidate: the published `0.9.0-pre.6` crate
(already in the local registry cache, `~/.cargo/registry/src/*/turso-0.9.0-pre.6`).
Every claim below is either read from the tag at `thirdparty/turso` (source path +
commit) or measured on this machine with the repo's own perf-lab; nothing comes
from a blog post. The engine still publishes **no release notes** (`CHANGELOG.md`
stops at 0.8.0), so the delta is derived from history, the tag's own docs, and
the A/B lab.

## 0. The range clone

`thirdparty/turso` was replaced with a clone holding **only** the range history
between the two tags, because the previous clone was a full 51 MiB history that
made every range query expensive:

```sh
cd thirdparty && rm -rf turso && mkdir turso && cd turso
git init -q .
git remote add origin https://github.com/tursodatabase/turso
git fetch --filter=blob:none --shallow-exclude=v0.9.0-pre.5 \
  origin refs/tags/v0.9.0-pre.6:refs/tags/v0.9.0-pre.6
git fetch --depth=3000 origin refs/tags/v0.9.0-pre.5:refs/tags/v0.9.0-pre.5
git switch --detach v0.9.0-pre.5     # the pin leas-db actually builds against
```

Result: 70 MiB of git data, both tags present, `HEAD`
at `v0.9.0-pre.5` so the working tree matches `thirdparty.toml` and the
dependency pin; `git switch --detach v0.9.0-pre.6` gives the candidate tree.
`git describe --tags --exact-match HEAD` = `v0.9.0-pre.5`, so `python3 refresh.py`
still matches the manifest's `ref` (only its `shallow = false` row now drifts —
the clone IS shallow, by design).

The `--depth=3000` pre.5 fetch is only there to validate ancestry
(`git merge-base --is-ancestor`) and to make `pre.5..pre.6` exact; a fresh
clone that only needs the diff takes the `--shallow-exclude` pre.6 fetch plus a
`--depth 1` pre.5 fetch (that pair reports 661 commits — the 12 missing ones are
boundary commits, recovered by `git fetch --deepen=80` on the pre.6 ref, after
which the count matches the API's 673). The old full clone was deleted, not kept
beside the new one.

## 1. Headline

Five things matter to `leas-db`, in order of measured or structural impact:

1. **The `NOT IN (SELECT …)` orphan-anti-join is 88× faster** in the repo's own
   lab with only the pin changed: 5.30 s → **60 ms** (§5). The per-miss NULL
   scan removal (`ecb4ea5`) is code-verified present at `pre.6` and absent at
   `pre.5`, and removing it is the leading explanation — not bisected, so
   `[INFERENCE]` on that causal step. The shipped `NOT EXISTS` rewrite stays
   faster (24 ms) and
   stays correct; this just removes the cliff if that shape ever returns.
2. **Batch import and single-row commits are ~15 % faster** on the same lab:
   WAL import 1.61 s → 1.35 s, MVCC import 2.41 s → 2.04 s, 500 one-row WAL
   transactions 234 ms → 189 ms (§5). RSS and the MVCC/WAL mode arithmetic are
   unchanged.
3. **`PRAGMA automatic_index` now exists and defaults ON** (`4b3befb`,
   `docs/sql-reference/pragmas.mdx`). It did **not** change any of our 17 hot
   statement plans — the sweep is byte-identical across pins (§5.4) — but it is
   a new *plan-changing default* and must be re-checked on every future bump.
4. **MVCC durability/recovery got materially safer** without changing the mode's
   arithmetic: one fsync removed per checkpoint, a crash between the two
   truncations of a TRUNCATE checkpoint now *completes* instead of failing closed
   with `Corrupt`, and every new logical log is LML3 (§3).
5. **No API break for anything `leas-db` calls.** `Builder`, `Database`,
   `Connection`, `Value`, `EncryptionOpts`, `prepare_cached`, `pragma_update`,
   `busy_timeout`, `execute` all keep their shape; the two removed public
   methods (`reload_dialect_schema`, `role_catalog`) are unused here. The
   resolved `Cargo.lock` diff is **only** the seven `turso*` version/checksum
   lines — no new package (§7).

## 2. MVCC: the real delta

The mode, its thresholds and its costs did **not** change. What changed is what
happens around durability and recovery. Concretely:

| Item | pre.5 | pre.6 | Evidence |
| --- | --- | --- | --- |
| Auto-checkpoint threshold | 4 120 000 B of logical log | identical (`DEFAULT_LOG_CHECKPOINT_THRESHOLD`, `core/mvcc/persistent_storage/logical_log.rs:275`) | source diff |
| Passive checkpoint | `experimental_mvcc_passive_checkpoint` flag required for `wal_checkpoint(PASSIVE)` | identical requirement (`core/translate/pragma.rs:1025`, `core/database.rs:3660`) | source |
| GC / checkpoint pragmas | `mvcc_checkpoint_threshold` (`-1` = off), `mvcc_gc_threshold`, `mvcc_group_commit` | identical; `-1` already accepted at pre.5 (`core/translate/pragma.rs:737-745`) | source diff |
| Checkpoint fsync count | truncate log → **fsync logical log** → truncate WAL | truncate log → truncate WAL. The log fsync is gone; the DB-file fsync before it is the durability point, and recovery skips old frames because their `commit_ts ≤ persistent_tx_ts_max` | `60c329e`; `docs/internals/mvcc/RECOVERY_SEMANTICS.md` |
| MVCC → WAL switch | checkpoint fsync | checkpoint **plus an explicit logical-log fsync** before the WAL-mode header, because a WAL-mode DB does not open while the log holds frames | `60c329e`, `MvStore::sync_logical_log` |
| TRUNCATE checkpoint crash window | killed between logical-log truncate and WAL truncate ⇒ header `NoLog` ⇒ **fail closed `Corrupt`, every later open fails** | that state is recognised and the checkpoint **completed** (backfill, fsync, fresh header, truncate WAL); `Invalid` still fails closed | `526f501`, `core/mvcc/database/mod.rs` |
| Interrupted checkpoint with a created table/index | root page recovered by decoding the rewritten `sqlite_schema` row after the pager commit (a fallible decode on the no-error path) | root page stored beside the rewritten row (`CreatedBtree`), read back at publish | `722a846` |
| Logical-log format | first write is LML2 until a portable-change frame rewrites the header to LML3 | **every new log starts LML3**; reading/upgrading old LML2 logs unchanged; releases ≥ v0.7.0 read LML3 | `e139e25`, `0db45d6` |
| Recovery of a log copied without the header rewrite | a log rebuilt from appended bytes stops at the first portable frame — commits after it lost until a checkpoint | fixed by starting at LML3 | `e139e25` (its tests) |
| Concurrent update | panic `read found a visible version but update could not supersede it` (`core/mvcc/cursor.rs:1995`) | panics removed for the reported interleaving | `7dd4026`, `0824670` |
| Embedder API | — | `Connection::storage_stats(&Arc<Self>) -> StorageStatsRead` (`page_size`, `page_count`, `freelist_count`, `logical_log_bytes`; under MVCC the counts are *as of the last checkpoint*, bytes since then are the log) and `Connection::disable_mvcc_auto_checkpoint()` (same as `PRAGMA mvcc_checkpoint_threshold = -1`, no SQL, no role check) | `50db016`, `core/connection.rs:306,2568,4962` |
| Prepared statements across checkpoints | — | a reprepared statement compiles against its transaction's schema; data-only checkpoints no longer invalidate prepared statements | `2a30ed1`, `tests/integration/mvcc/checkpoint.rs:709` |

What this does to our integration points:

- `crates/leas-db/src/database.rs` reads byte 19 of the file header
  (`255` = MVCC, `2` = WAL) and pairs the MVCC opt-in with
  `experimental_mvcc_passive_checkpoint(true)`. Both behaviours exist unchanged
  at pre.6, so that logic needs no edit.
- `remove_stale_mvcc_log_for_wal` deletes a `<db>-log` left next to a WAL-mode
  file. The LML3 change does not touch the file extension or the journal-mode
  byte, so the heuristic still holds.
- The one-fsync-per-checkpoint saving is on the **MVCC** path only; the default
  WAL path is untouched. On our batch-end `wal_checkpoint(PASSIVE)`
  (`ops/ping.rs`, `database.rs::checkpoint_passive`) it removes one fsync per
  batch, not per commit `[INFERENCE]` — small on any disk, invisible in the
  wall numbers below.
- The recovery change is the one real behavioural delta: a database that was
  *permanently unopenable* under pre.5 after a kill in the truncate window now
  opens and finishes the checkpoint. That is worth the bump on its own for the
  MVCC opt-in.

MVCC arithmetic itself did **not** move (§5.1–5.3): the import burst still costs
~1.5× WAL wall, ~2× WAL CPU and ~2.3× peak RSS, and the read tail is still
several times WAL's. Nothing in pre.6 changes ADR 0014's workload verdict.

## 3. Query path: planner, execution, formatting

### 3.1 `PRAGMA automatic_index` (new, default ON)

`4b3befb` implements what SQLite's `automatic_index` does for a join: when the
right side of a join would be a full scan and the already-joined tables supply
equality terms, Turso builds an **ephemeral B-tree** on it once and probes it
(`core/translate/optimizer/access_method.rs:978`,
`core/translate/main_loop/close.rs::emit_autoindex`). The merge itself states the
first step covers tables; later commits in the range extend it to a
materialized FROM-clause subquery (`find_best_access_method_for_subquery`,
`access_method.rs:1913`), add `skip automatic index for subqueries when pragma
is off` (`0b3527b`), and fix WITHOUT ROWID distinctness in the ephemeral key
(`0ab78f9`). It is **not** applied to a RIGHT/FULL join's right side, and it
does not rewrite `IN (SELECT …)`.

Why it is a risk and not a win for us: three of our hot statements are joins
(`profiles_query.rs:1298`, `export.rs:236`, `endpoint_rank.rs:1178`), but every
join key is a PK/autoindex (`endpoints(id)`, `profile_stats(endpoint_id)`,
`protocols(id)`, `endpoint_rank(endpoint_id)`), so the arm never fires — the
plan sweep is identical across pins (§5.4). The knob is worth remembering when a
future query joins an unindexed column: it will silently build an ephemeral
index instead of an N² scan, which is usually right but is a plan change nobody
reviewed.

### 3.2 The `IN (SELECT …)` NULL scan (`ecb4ea5`)

The translator emitted, on every *miss*, a walk of the whole materialized list
to learn whether it contains a NULL (`IN` returns NULL rather than false when it
does). That walk is loop-invariant for a single-column IN. pre.6 checks only the
first row (`NULL` sorts first in an ephemeral index), exactly as SQLite's
`sqlite3SetHasNullFlag` does; row-value IN keeps the walk because `(1, NULL)`
only yields NULL for some left-hand values. Our tuple form —
`(protocol_id, endpoint_id) IN (…)` at `database.rs:575` — is row-value IN, so
this fix does **not** cover it; the single-column lists (`endpoint_id IN (…)`
throughout `database.rs`/`endpoint_ip.rs`) are the covered shape. Verified in
the two trees:
`core/translate/expr/translator.rs` at pre.6 branches on `lhs_column_count == 1`
and emits `Rewind → IsNull(lhs) → Column(first) → IsNull`, while pre.5 always
emits `label_null_checks_loop_start` / `label_null_checks_next`.

The commit's own measurement: `x IN (SELECT …)` with 20k outer rows and 1000
list rows, most missing — 6.4 s → 0.14 s (debug build). Our real-schema lab
reproduces the same class of win at 74k/70k: **5.30 s → 60 ms** (§5.3). In the
standalone control the plan text is identical on both pins (`LIST SUBQUERY 1`,
`SCAN protocols`); the real lab does not print its plan, so what the real schema
selects at pre.5 is inferred, not observed. A minimal 74k/70k schema on either
pin never selects that bytecode shape (55–62 ms on both), which is why a
standalone reproduction does not show the delta — the win is
plan-selection-dependent, so measure it on the real schema, not on a toy one.

### 3.3 Prepare/plan and scalar CPU (CodSpeed numbers, no plan change)

Two large merges add CPU work removal with no semantic change. From their own
commit messages (CodSpeed simulation = callgrind instructions weighted by cache):

- `624ed32` — prepare/plan: `corpus_job[24b]` 610 ms → 98.6 ms (−84 %),
  `corpus_tpcds[85]` 85.9 → 10.7 ms (−88 %); suite geometric mean −28.8 % time /
  −33.8 % instructions over 302 prepare benchmarks; `Open/Connect`
  133.85 → 104.41 ms (−22 %); batch inserts −8.9…−12.3 %; concurrent writes (WAL)
  −3.8 %. The MVCC insert benchmarks are 1.5–2.5 % slower there (non-inlined
  CAS), i.e. noise for us.
- `1b56ac8` — 30 commits: datetime 9–43 % faster, `timediff` ~70 %, float
  formatting up to 71 %, integer→text up to 58 %, LIKE/GLOB byte matchers
  35–65 %, `replace`/`concat`/`substr`/`trim` 20–35 %, multi-row INSERT prepare
  up to 20 %.

What reaches `leas-db`: page reads and the bulk writers go through
`prepare_cached`/raw literal statements — parsing is a small part of a 19–35 ms
page read, but `Open/Connect` and the import arms moved measurably (§5.1). The
scalar work is irrelevant to this schema (no `strftime`, little `LIKE`).

### 3.4 DISTINCT (new optimizations, no local user)

- `d8ab111` — use index order for `SELECT DISTINCT`/`count(DISTINCT x)` when an
  index already sorts the key: 2–2.3× at 10k–1M rows, up to 14.8× on a
  high-cardinality `count(DISTINCT)`; the hash table is dropped
  (`EXPLAIN` no longer says `USE HASH TABLE FOR DISTINCT`).
- `31f6c1b` — drop DISTINCT entirely when the selected columns are already
  unique (rowid/INTEGER PK/unique NOT NULL): `count(DISTINCT id)` 91–399×,
  `SELECT DISTINCT id, name` 8.5× at 1M rows, peak RSS 182 → 20 MB.

Our only aggregate is `SELECT group_id, COUNT(*) … GROUP BY group_id`
(`Database::get_group_member_counts`, 0.9 ms at 20k memberships). No `DISTINCT`
in the crate's SQL. Nothing to adopt; listed so the absence is a decision.

### 3.5 Storage / B-tree / schema

- `7fbac6d` + `5e6150f` — schema copies share tables/indexes/views/triggers
  behind `Arc`; ALTER TABLE RENAME −26 %, RENAME COLUMN −23 % (CodSpeed); MVCC
  inserts −1.1…−2.5 %. `push_schema` runs at cursor 0 only, so this buys us
  nothing except a faster first-run DDL.
- `d827467` — table-leaf cells that overflow are padded like index leaves
  (space/correctness, not speed).
- `6b6e8ef`, `9833b0f` — `wal_get_frame` rejects uncommitted frames and reads
  under a read lock (WAL/pager robustness).
- `fdcf4bb` — multiprocess-WAL probe slot advances past frames a reader cannot
  see. We compile the feature (`experimental_multiprocess_wal`) but never enable
  it; no action.
- `bed55ac` — a checkpoint whose DB-file writes fail now **fails** (previously:
  never returns, or reports backfilled pages that never reached the file). Only
  reachable on a full disk; it turns a hang into an error, which our
  `retry_on_busy`/error path can surface.
- `core/schema/sqlite_schema_rows.rs` + `core/mvcc/sqlite_schema_row.rs` (new,
  864 lines) — one decoder for `sqlite_schema` rows used by the MVCC checkpoint
  and schema build; `Corrupt` on a malformed row version instead of a panic.

## 5. Measurements on this machine

Method: the repo's own lab, `crates/leas-db/tests/turso09_lab.rs`, release build,
system allocator, same machine and same data for both pins; the only change
between arms is the `turso` version in `crates/leas-db/Cargo.toml`, reverted
immediately after each arm (`git checkout -- crates/leas-db/Cargo.toml Cargo.lock`).
No repo pin was changed by this study.

Engine versions under test: pre.5 tag `98dc77b` (also the repo pin) and pre.6
tag `8f00aac`. The measurements ran against the **published crates**; the
pre.6 crate's `.cargo_vcs_info.json` names the tag sha `8f00aac`, and
`translate/optimizer/access_method.rs`,
`mvcc/persistent_storage/logical_log.rs` and `translate/expr/translator.rs` are
byte-identical between the crate and the tag tree, so the crate is the tree this
study read.

```sh
cargo test -p leas-db --release --features perf-lab --test turso09_lab -- \
  --ignored --nocapture <arm>
```

Each figure is a single run. Treat ±10 % as noise; the 88× is not.

### 5.1 Import burst (+20k rows over 40k preseed, one page reader beside it)

| Arm | pre.5 | pre.6 | Δ |
| --- | --- | --- | --- |
| WAL wall | 1.61 s | **1.35 s** | −16 % |
| WAL CPU | 1 920 ms | **1 760 ms** | −8 % |
| WAL peak RSS | 71 MiB | 71 MiB | 0 |
| MVCC wall | 2.41 s | **2.04 s** | −15 % |
| MVCC CPU | 3 770 ms | **3 440 ms** | −9 % |
| MVCC peak RSS | 167 MiB | 162 MiB | −3 % |
| MVCC disk after burst | db 19 688 KiB + wal 12 271 + log 430 | db 15 664 KiB + wal 12 271 + log 430 | smaller DB file |

The WAL/MVCC ratios are unchanged (wall 1.5×, CPU ~2×, RSS ~2.3×), so this is a
uniform speed-up, not a mode shift.

### 5.2 One-row commits and reader contention

| Arm | pre.5 | pre.6 |
| --- | --- | --- |
| 500 one-row txns, WAL | 234.1 ms, 160 ms CPU, 0 fails | **188.7 ms**, 160 ms CPU, 0 fails |
| 500 one-row txns, MVCC | 115.1 ms, 140 ms CPU, 0 fails | 129.6 ms, 160 ms CPU, 0 fails |
| contention WAL: quiet p50 / during p99 / stall | 140 µs / 624 µs / 4.5× | 147 µs / 596 µs / 4.1× |
| contention MVCC: quiet p50 / during p99 / stall | 167 µs / 2.51 ms / 15.0× | 168 µs / 3.75 ms / 22.3× |

The single-row WAL win is consistent with the cheaper statement/prepare path
`[INFERENCE]`; the MVCC single-row numbers swap places within noise. The MVCC read tail was worse in this
run (3.75 vs 2.51 ms p99) and better in others; one burst each is not enough to
call a direction — the stable fact across pins and runs is that MVCC's tail is
2–5× WAL's, which is what ADR 0014 already encodes.

### 5.3 The orphan anti-join (`config_width_anti_join`)

`SELECT count(*) FROM protocols WHERE NOT (id IN (SELECT protocol_id FROM
profile_stats))` vs the `NOT EXISTS` rewrite, 74 000 protocols / 70 300 links
(5 % orphans), real toasty schema:

| Feed | pre.5 | pre.6 |
| --- | --- | --- |
| wide config (22 720 KiB table): `NOT IN` | **5.30 s** | **60.33 ms** |
| wide config: `NOT EXISTS` | 23.82 ms | 24.93 ms |
| narrow config (17 540 KiB): `NOT IN` | **5.30 s** | **60.11 ms** |
| narrow config: `NOT EXISTS` | 23.12 ms | 24.92 ms |

This is the study's decisive result: the shape the prior delta study recorded
(5.37 s vs 23.5 ms) now runs within 2.4× of the rewrite instead of 230×. The
`NOT EXISTS` rewrite still wins and stays shipped — it is also the shape that
does not depend on a planner decision.

Control: a 3-table standalone reproduction (74k/70k, `INTEGER PRIMARY KEY`
endpoints, `(protocol_id, endpoint_id)` PK, index on `protocol_id`, `id NOT IN`
**and** `NOT (id IN …)` spellings) answers in 54–62 ms on **both** pins. The
engine picks a different (hash) path there, so that lab cannot see the fix;
it rules out the spelling and the index as explanations. `[INFERENCE]` the delta
lives in the plan the real schema selects, which pre.6 executes without the
per-miss walk; the real lab does not print that plan, and a bisect across engine
commits was not run.

Caveat: all three lab arms run WAL. Pre.5 measured 5.39 s under MVCC; pre.6's
MVCC arm is unmeasured (the fix is in translation, i.e. mode-independent).

### 5.4 Plan sweep (the only check that catches `automatic_index` drift)

`plan_sweep` prints `EXPLAIN QUERY PLAN` for 17 statements (purge candidates and
re-check, page count/ids/projection, rank reads, repair, group counts/members,
export projection, IP reads and seeks, reband, stability seed, error sweep).
Between pins the output is **byte-identical** (`diff` of the `PLAN2` lines →
empty). So on this schema the new default built no ephemeral index, and the
`NOT IN` change altered no plan either.

## 6. What `leas-db` should do, ranked

### 6.1 Bump the pin (recommended)

Low risk, measurable gains, one behavioural fix worth having:

- no API used by `crates/leas-db/src/driver/` changed; the two removed public
  methods are unused;
- file format and the journal-mode byte are unchanged; an existing WAL or MVCC
  file opens as before;
- plan sweep identical, so no index work is needed to land it;
- import −15…−16 %, 500 one-row WAL txns −20 %, `NOT IN` 88× faster, MVCC
  recovery fixed.

Verification set for the bump (each is one existing lab arm, seconds to a minute):
`config_width_anti_join`, `import_wal_vs_mvcc`, `single_row_wal_vs_mvcc`,
`reader_contention_wal_vs_mvcc`, `plan_sweep`, plus the normal
`cargo nextest run -p leas-db`.

Risks to state in the bump commit:

- `automatic_index` is ON by default: the plan sweep above is the guard, and it
  must be run again, not assumed;
- the LML3 header means an MVCC database written by pre.6 is only readable by
  turso ≥ v0.7.0; pre.5 already reads and writes LML3 (it upgrades an LML2 log
  in place), so this is not a break for any pinned crate in this repo — a
  downgrade to pre.5 still opens the file;
- the logical log is no longer fsynced at checkpoint; the DB-file fsync and the
  `commit_ts ≤ persistent_tx_ts_max` recovery rule carry durability
  (`RECOVERY_SEMANTICS.md` is the contract).

### 6.2 Keep the `NOT EXISTS` rewrite

Still 2.4× the `NOT IN` shape at 74k, and it does not depend on the NULL-scan
fix staying correct. The comment at `database.rs:2855` should be updated to say
the 5.3 s figure is a pre.5 property (60 ms at pre.6) so the next reader does not
treat a stale number as current.

### 6.3 Optional: own the MVCC checkpoint window during an import

`Connection::disable_mvcc_auto_checkpoint()` lets a bulk import finish its
burst without a threshold-crossing checkpoint in the middle, then run the
existing batch-end `PRAGMA wal_checkpoint(PASSIVE)`. Do not adopt blind: under
MVCC the checkpoint is what frees versions, and `mvcc_checkpoint_threshold = -1`
across a long session grows the logical log (memory + reopen cost) — the import
arm must show a stall worth removing first. Under WAL nothing changes (the
threshold is MVCC-only).

### 6.4 Optional: `storage_stats` for a DB readout

It answers "how big is the DB" without SQL and without a role check; under MVCC
it also reports the logical-log bytes, which is the one number that explains an
apparent disk/memory discrepancy. Nothing in the app displays size today, so
this is a feature, not a fix; if it is added, it is one call on the existing
connection, no schema work.

### 6.5 Do nothing about

DISTINCT ON, `UPDATE … SET = DEFAULT`, sequences, `foreign_key_check`,
PostgreSQL frontend, `tursopg`, Turso Cloud `sync`, `mpwal`, CDC/portable logs,
Row-Level Security, materialized views. None has a caller in this crate, and
each would add surface for no measured gain.

The manual-SQL workarounds also stay: `COMPAT.md` at pre.6 still lists in-place
`VACUUM` and `auto_vacuum` as experimental and `incremental_vacuum` as
unsupported, so `ops/compact.rs` and `ops/purge.rs` keep the shapes they have.
The same `COMPAT.md` still gates MVCC's passive checkpoint behind the
experimental flag, so the app's pairing in `database.rs:286-300` remains
required — MVCC did not become cheaper by default in this range.

## 7. Upgrade checklist (the practical form of §6.1)

1. `crates/leas-db/Cargo.toml`: `turso = "=0.9.0-pre.6"`.
2. `cargo build -p leas-db` — the driver touches only stable API; expect a clean
   build. The lock diff is measured, not predicted: `cargo metadata --offline`
   after a trial bump changed **only** the `turso`, `turso_core`, `turso_ext`,
   `turso_macros`, `turso_parser`, `turso_sdk_kit`, `turso_sqlite` version and
   checksum lines (23 diff lines, no `name` added or removed).
3. `cargo nextest run -p leas-db` (unit + integration + migration tests).
4. The six lab arms in §6.1 at the new pin; compare against the pre.5 numbers in
   §5 (the lab prints one line per arm).
5. Open one copy of a real `LEAS` database file in each mode (WAL, MVCC) and let
   the app reconcile once — schema cursor, `invalid_shapes_purged` and the
   capability sweep are engine-independent but cheap to prove.
6. `thirdparty.toml` / `python3 refresh.py --sync` only if the reference clone
   is meant to move with the dependency; the research clone already carries both
   tags.

## 8. Limits of this evidence

- One machine, release build, system allocator, one run per arm. The import and
  single-row deltas are 8–20 %, inside the range that a shared machine can
  distort; the 88× anti-join delta and the identical plan sweep are far outside
  it.
- The lab's feed is synthetic at the dump's scale (74k protocols, 20k-row
  bursts), not the operator's file: same statements, different distribution.
- The `NOT IN` win is measured under WAL only, and its mechanism
  (`ecb4ea5`) is a translation change — but the size of the win depends on the
  chosen plan, so a different schema could see 2× instead of 88×.
- Upstream's prepare/function/DISTINCT numbers are CodSpeed *simulations* on
  their corpora, quoted from the merge messages, not reproduced here; only the
  lab arms in §5 were run.
- The crash-recovery behaviours (TRUNCATE-window completion, checkpoint write
  failure) are read from the commits and their tests, not injected here. They
  are the reason to prefer the bump even where walls are noise.
